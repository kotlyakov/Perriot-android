## Контракт реализованного компонента

`chooseApkBoss(rng, {ante=1, winAnte=8, bossesUsed={}, bannedKeys=[]})` возвращает `{bossId, bossesUsed, rng}` без изменения входных объектов. `bossId` — исходный ключ `bl_*`; `bossesUsed` содержит счётчики всех 28 боссов. Пропущенные счётчики во входе означают начальный ноль. Все выходные данные сохраняются обычным JSON.

Поддержан обычный выбор полной версии: анте — неотрицательное безопасное целое; `winAnte` — положительное безопасное целое; счётчики — неотрицательные безопасные целые с запасом для увеличения на единицу. `bannedKeys` содержит ключи блайндов каталога, включая при необходимости Small/Big (они и без банов не входят в выбор). Баны других типов контента следует отфильтровать до вызова. Неизвестные параметры и некорректные значения явно отклоняются.

Не поддержаны принудительный `FORCE_BOSS`, разовое назначение `perscribed_bosses`, учебное ограничение `FTP_LOCKED`, а также отрицательное анте. Это отдельные исходные ветки с иным поведением RNG/счётчиков; их нельзя считать реализованными этим компонентом.

## Правила выбора

1. Обычный босс доступен при `min <= max(1, ante)`. Финальные боссы выбираются только при `ante >= 2` и кратности `winAnte`. При стандартном `winAnte=8` это анте 8, 16, 24 и далее; при `winAnte=4` — уже анте 4. Записанные в каталоге `max=10` и `min=10` финальных боссов **не ограничивают** эту ветку исходного выбора.
2. Из допустимых кандидатов удаляются баны. Флаг `demo`, открытие/победа над боссом и наличие реализации его эффекта не фильтруют обычный пул.
3. Остаются кандидаты с наименьшим числом предыдущих назначений. Счётчик увеличивается при назначении, а не при победе. Как в исходнике, первоначальная верхняя граница поиска минимума равна 100; если все допустимые счётчики выше 100, пул пуст. Компонент выдаёт явную ошибку вместо сбоя исходного случайного выбора. При полном бане пул также вызывает ошибку; RNG не расходуется.
4. Ключи оставшихся кандидатов сортируются лексикографически, независимо от порядка показа в коллекции.
5. Продвигается единственный поток `boss`, результат `pseudoseed('boss')` пересоздаёт глобальное состояние LuaJIT RNG. Из него берётся одно целое `math.random(N)` с единственной границей. Возвращается это продвинутое глобальное состояние, а не прежнее. Последующий неключевой RNG зависит от назначения босса.

Каталог содержит 30 блайндов: 2 обычных блайнда, 23 обычных босса и 5 финальных. Обычная награда: Small — $3, Big — $4, боссы — $5; финальные — $8. Множитель цели: Small 1, Big 1.5, Needle 1, Wall 4, Violet Vessel 6; все остальные боссы 2. Множитель — факт каталога, а не реализация полного вычисления цели.

## Проверка

`node --test tests/core/apk-blinds.test.js`: 7 тестов. Первые 5 тестов выполнены до реализации и падали из-за отсутствующего компонента; после реализации проходят. Покрываются полный состав каталога, каждый из 28 боссов, наименьшее использование, баны, граничные анте, Endless/custom winAnte, отсутствие мутации, продолжение из JSON и ошибки входа/пустого пула.

Дополнительный независимый эталон: оригинальные функции `get_new_boss`, `pseudoseed`, `pseudohash`, `pseudorandom_element` и оригинальная таблица блайндов исполнены вне репозитория в нативном Linux x64 LuaJIT `2.1.1700008891`, собранном ранее из закреплённого upstream-коммита `43d0a19158ceabaa51b0462c1ebc97612b420a2e`. Параметры адаптера: `FTP_LOCKED`/`FORCE_BOSS` отсутствуют, нет назначенных боссов и банов, `win_ante=8`, все счётчики изначально нулевые.

В тесте встроены 72 последовательных результата: для семян `PIERROT1`, `AAAAAAA1`, `ПЬЕРО1`, по анте 1–24. Для каждого назначения проверяются исходный ключ босса, точное состояние потока `boss` и следующий неключевой `math.random`. После контрольного неключевого значения продолжается следующий выбор. Все совпадают с JS. Это изолированный эталон численной логики, **не запуск Android APK** и не доказательство полной эквивалентности встроенного бинарного рантайма, порядка всех игровых событий или всех эффектов боссов.

Полный пул назначений реализован независимо от полноты игровых эффектов. Подключение компонента к старту/следующему анте, сохранению и интерфейсу выполняется отдельно; эта записка сама по себе не утверждает такую интеграцию.
