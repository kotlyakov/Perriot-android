## Подтверждённые правила Tag

Пул имеет 24 исходные позиции, упорядоченные по `order`. Неподходящие записи сохраняют позицию как `UNAVAILABLE`. Не следует сжимать пул перед случайным выбором. Условия:

- Минимальное анте 2 у Negative, Standard, Meteor, Buffoon, Handy, Garbage, Ethereal, Top-up, Orbital. У остальных минимальное анте в источнике отсутствует.
- Rare требует обнаруженный `j_blueprint`; Negative, Foil, Holographic, Polychrome требуют обнаруженные `e_negative`, `e_foil`, `e_holo`, `e_polychrome` соответственно. Состояние обнаружения самого тега не является условием.
- Баны исключают соответствующие позиции. Если весь пул недоступен, исходник всё равно выдаёт резервный `tag_handy`, даже если он запрещён или анте меньше 2.
- Первое обращение использует поток `Tag{ante}`. Попадание в `UNAVAILABLE` вызывает `Tag{ante}_resample2`, затем `...3` и так далее. Нумерация попыток начинается заново для каждого выбора; состояния уже существующих потоков продолжаются.
- Выбор по одному потоку не мешает другому тегу получить ту же награду; выбранные теги не удаляются из пула.
- Каждая попытка пересоздаёт глобальное RNG из `pseudoseed` и расходует один `math.random(N)`. Следующее неключевое значение зависит от последней фактической попытки.

Два независимых запуска закреплённого нативного процесса дали полностью одинаковые все 36 пулы, 144 выбранных тега, состояния потоков и проверяемые случайные числа. Порядок 24 тегов определяется метаданными `order`, не хеш-порядком `pairs`.

## Орбитальный выбор: точный RNG и ограничение порядка

В исходном UI массив видимых рук создаётся обходом `pairs(G.GAME.hands)`, без сортировки по силе/названию/полю `order`. Затем исходный `pseudorandom_element` выбирает позицию массива из потока `orbital`. Численный алгоритм точно воспроизводится **при одинаковом массиве видимых рук**.

Обнаружено существенное ограничение: два запуска одного и того же закреплённого нативного исполняемого файла с тем же исходным конструктором таблицы дали разные порядки `pairs`:

| Запуск | Порядок видимых рук |
| --- | --- |
| Первый | Full House, Two Pair, Straight Flush, Flush, Pair, High Card, Straight, Four of a Kind, Three of a Kind |
| Второй | Pair, Straight, Straight Flush, Three of a Kind, High Card, Full House, Two Pair, Four of a Kind, Flush |

Для тех же семян численные позиции, все значения RNG и состояния потоков совпали, но названия выбранных орбитальных рук изменились. Поэтому **семени забега недостаточно для обещания совпадения названия руки между исходными процессами**. Эталонные записи сохраняют фактически наблюдённый массив, который передаётся в JS как `visibleHandOrder`. Порядок по умолчанию в реализации — её фиксированное решение, а не доказанный единственный порядок оригинального Android-процесса.

Сохранение должно включать выбранные орбитальные руки и порядок видимых рук для последующих выборов. Оригинальный UI хранит результат в `orbital_choices[ante][blindType]`; при повторном показе существующего слота он не обращается к RNG. Чистый `chooseApkOrbitalHand` выполняет новый выбор при каждом вызове; кеширование и использование сохранённого результата принадлежат интеграции. Проверка JSON в эталонном тесте подтверждает сохранность выбранной руки, массива и последующего выбора, но не является тестом игрового UI/системы сохранения целиком.

## Порядок при старте

Статически подтверждён исходным `game.lua:2376–2379`: при новом забеге без принудительных учебных значений выбираются **босс → ваучер → тег Small → тег Big**. Орбитальный выбор в этих строках отсутствует: он создаётся позднее при построении UI выбора блайнда и только для ещё незаполненного слота. Эталонные тесты этого файла проверяют чистые компоненты, не весь старт/создание колоды/отрисовку. Тесты интеграции отдельно проверяют сохранение стартовых выборов и отсутствие повторной генерации. Полная последовательность старта не прогонялась целиком в нативном оригинальном рантайме.

## Результат проверки

Команда: `node --test tests/core/apk-tags-oracle.test.js`, **3 теста проходят**.

Встроенный эталон: 3 семени (`PIERROT1`, `AAAAAAA1`, `ПЬЕРО1`) × анте 1/2/8 × 4 состояния (нет обнаружений, все 5 обнаружений, только Blueprint/Foil/Polychrome, все теги запрещены) = **36 контекстов**. Для каждого выполнены 4 последовательные операции Tag → неключевой RNG → orbital → неключевой RNG: всего **144 пары выборов**, 288 контрольных неключевых значений, с проверкой точного словаря всех продвинутых потоков. Дополнительно проверяется зависимость результата руки от перестановки массива при неизменном RNG и продолжение после JSON-снимка.

Не проверены этим эталоном: `FORCE_TAG`, учебные принудительные награды, необязательный исходный `append`, эффекты полученных тегов, появление ранее скрытых типов рук в игре, полный порядок игровых событий и Android UI.
