# REPOSITORY_RULES.md — GitHub workflow для проекта Pierrot

**Репозиторий:** `kotlyakov/Perriot-android` (private). **Основная ветка:** `main`.
**Область действия:** все задачи по разработке, исправлениям, тестам, сборке и документации Pierrot.
**Приоритет:** явное решение пользователя > AGENTS.md (игровые требования) > ROADMAP.md (план) > этот файл (Git-процесс). При конфликте сообщить пользователю, не подменять требования.

## 1. Автономность и доступ
- При каждой задаче самостоятельно проверять доступ к репозиторию, читать актуальный HEAD и относящиеся к задаче файлы. Не просить пользователя вручную коммитить или загружать файлы, если запись через GitHub-инструменты доступна.
- Использовать подключённые GitHub-инструменты для чтения, создания веток, файлов, коммитов, PR и слияния. Если доступен полноценный git/рабочая среда — применять `git fetch`, `git status`, `git diff`, `git push`; иначе выполнять эквивалентные операции через GitHub API. Не заявлять о выполнении `fetch/push`, если фактически использовался только API.
- После изменения прав доступа повторять проверку. Если API возвращает 403/404 или инструмент отсутствует — показать точную ошибку и предложить минимальный обходной путь. Не выдавать локальную подготовку за опубликованное изменение.
- Работать только с `kotlyakov/Perriot-android`; не создавать публичные копии и не менять visibility без отдельного разрешения.

## 2. Начало каждой задачи: синхронизация
1. Получить сведения о репозитории, default branch и текущем HEAD; прочитать `AGENTS.md`, `ROADMAP.md`, документацию системы и последние релевантные изменения, если файлы существуют.
2. Проверить рабочее дерево (при git) и наличие чужих/незавершённых изменений. Ничего не удалять и не перезаписывать без выяснения происхождения.
3. Сопоставить задачу с утверждёнными пользовательскими решениями. Утверждённый UI, анимации, поведение и эталонные версии не менять без запроса.
4. Создать ветку от свежего `main`: `feat/<slug>`, `fix/<slug>`, `test/<slug>`, `docs/<slug>`, `ci/<slug>`. Существующую ветку повторно использовать только если это та же незавершённая задача.
5. Не начинать работу на устаревшей базе. При изменении `main` синхронизироваться перед слиянием.

## 3. Реализация и коммиты
- Делать минимальные, осмысленные изменения; не смешивать независимые задачи.
- После логического шага проверять diff, запускать доступные тесты, затем коммитить. Сообщения: `feat: ...`, `fix: ...`, `test: ...`, `docs: ...`, `ci: ...`, `refactor: ...`.
- Если GitHub API не предоставляет индекс/стейджинг, использовать операции создания/обновления файлов и Git objects с контролем актуального SHA. Для изменения файла предварительно получить его SHA.
- При git: `git fetch origin`, `git switch -c ... origin/main`, выборочное `git add`, `git commit`, `git push -u origin <branch>`. Не использовать `git add -A` вслепую.
- Каждый коммит должен оставлять проект в согласованном состоянии. Не добавлять временные APK, логи, кеши и build output, если это явно не утверждённый способ хранения артефактов.
- После коммита проверять, что он появился в удалённом репозитории, и фиксировать SHA.

## 4. Pull request, review, merge
1. По завершении задачи открыть PR из рабочей ветки в `main` с кратким описанием, тестами, рисками и ссылкой на задачу/этап ROADMAP.
2. Проверить CI и статус PR. Если доступно, провести независимую проверку diff на регрессии и безопасность.
3. Автоматически сливать обычные изменения **только после успешных обязательных проверок**, если пользователь заранее утвердил направление работы и нет новых спорных решений.
4. Изменения архитектуры, игрового баланса, ранее утверждённого дизайна, удаление данных, переписывание истории и публикация релизов требуют отдельного согласования.
5. После merge получить новый HEAD `main`, убедиться, что изменения вошли, и обновить ROADMAP/progress. Удалять только собственную уже слитую временную ветку.
6. Если PR/merge недоступен через инструмент, не обходить защиту веток прямой записью в `main`; сообщить о блокировке.

## 5. Конфликты и параллельная работа
- Перед интеграцией сравнить текущий `main` с базой ветки. При необходимости сделать merge/rebase в рабочей ветке, но никогда не force-push в `main`.
- Автоматически разрешать только очевидные независимые правки с последующим полным тестированием. Для конфликтов в правилах игры, числах, сохранениях, утверждённом UI, build/signing и зависимостях — анализировать обе версии; если корректный выбор не доказуем, спрашивать пользователя.
- Не применять `ours/theirs` ко всему проекту и не отбрасывать чужие коммиты.
- Если ветка изменилась одновременно, повторно получить HEAD и SHA; не делать принудительную запись поверх чужой работы.
- При параллельных агентах разграничивать владение файлами и интегрировать их изменения последовательно.

## 6. Тестирование и Android APK
- Для игрового ядра: детерминированные тесты правил, RNG, очков, экономики, сохранения и регрессии.
- Для UI: проверять утверждённые сценарии, адаптацию к экрану, жесты, подсказки, анимации, переполнение чисел.
- Для Android: GitHub Actions/Gradle; APK проверять официальными `apksigner verify` и `zipalign -c`. Не применять самодельную подпись и не утверждать, что APK устанавливается, пока это не проверено на устройстве.
- Debug-подпись может меняться между CI-запусками: предупреждать о необходимости удаления предыдущей версии, если сертификат иной. Для обновлений поверх установленной версии требуется стабильный ключ подписи.
- Секреты, keystore, токены и приватные материалы не коммитить. Использовать GitHub Actions Secrets и минимальные permissions.
- Оригинальные APK и чужие изображения/звуки использовать лишь как исследовательский референс; не помещать в исходники/релиз без соответствующих прав.
- При падении тестов исправлять причину и повторять проверки. Не помечать задачу «готово» при красном CI.

## 7. Защита данных и история
- Не удалять ветки `legacy/*`, теги утверждённых сборок и референсы без согласования. Ветку/тег создавать только когда подтверждено соответствие исходников указанной версии.
- Не использовать `push --force`, `reset --hard`, `clean -fd`, удаление репозитория, массовое удаление файлов или изменение видимости без явного разрешения.
- Изменения схемы сохранений делать с миграцией и тестами совместимости.
- Никаких фиктивных результатов тестов, коммитов, PR, сборок и релизов.

## 8. Отчёт после каждой задачи
Кратко сообщать: что изменено; ветка и SHA коммита; PR и результат merge; тесты/CI (проверено или не запускалось); ссылка на APK при наличии; известные проблемы и следующий шаг. Не выдавать намерения за выполненную работу.

## 9. Первая настройка нового репозитория
- Убедиться, что репозиторий private и доступна запись.
- Добавить исходники приложения, `AGENTS.md`, `ROADMAP.md`, этот файл и `.gitignore`.
- Проверить GitHub Actions, Gradle wrapper, Android SDK и сборку baseline.
- Настроить правила защиты `main` и обязательные проверки, когда они появятся.
- Только после успешной сборки и подтверждения пользователем продолжать наращивать функциональность.
